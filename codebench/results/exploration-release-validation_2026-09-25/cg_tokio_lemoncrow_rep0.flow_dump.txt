[assistant] Tokio (multi-thread scheduler, source in `tokio/src/runtime/scheduler/multi_thread/`):

**Structure.** A fixed pool of worker threads. Each worker owns a `Core` with a bounded local run queue (`queue.rs`, `LOCAL_QUEUE_CAPACITY`) plus a single-task **LIFO slot** (`lifo_slot`). One shared **inject queue** (global MPMC) and an `Idle` set track parked workers.

**Scheduling a task** (`handle.rs::schedule` → `Core::schedule_task`):
- Called when a task is spawned or woken. If the current thread is a worker, the task goes into that worker's `lifo_slot` (the previous slot occupant is bumped to the local queue). Checking the LIFO slot *before* the run queue means the most-recently-woken task runs next — optimizes message-passing locality/latency.
- If not on a worker thread (external wake), it goes to the **inject queue**.
- If the local queue is full, `push_back_or_overflow` spills the new task plus half the local queue into the inject queue.
- After pushing, a parked worker is unparked (`notify`) if work needs stealing.

**Running** (worker run loop, `worker.rs`): each worker repeatedly picks next task by priority:
1. LIFO slot (with a budget cap so it can't starve the queue),
2. local run queue,
3. periodically the inject queue (every Nth tick, for fairness),
4. **work-stealing**: if local is empty, steal ~half of another random worker's queue (`steal_into`),
5. else check inject/global, then **park** (register in `Idle`, sleep on the driver/IO).

**Fairness & cooperation.** A per-task budget (`task::coop`) forces long-polling tasks to yield; the `tick` counter forces periodic inject-queue and maintenance checks so global/IO work isn't starved.

**current_thread** scheduler (`current_thread/mod.rs`) is simpler: one queue, no stealing, driven by the thread that calls `block_on`.
