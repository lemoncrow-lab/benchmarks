[assistant] Django separates the *lazy description* of a query (`QuerySet`/`Query`) from *SQL generation* (`SQLCompiler`) from *execution* (DB cursor). The pipeline:

**1. Build — `QuerySet` is lazy.** Each `.filter()`, `.exclude()`, `.annotate()`, `.order_by()`, etc. (`django/db/models/query.py`) clones the QuerySet and mutates its inner `Query` object (`django/db/models/sql/query.py`) — no DB hit. `filter()` calls `Query.add_q()` → `build_filter()`, which resolves field paths, sets up joins in `alias_map`, and appends `Lookup`/`WhereNode` nodes to `query.where`. State lives on the `Query`: `where`, `alias_map`, `select`, `group_by`, `order_by`, `low_mark/high_mark` (slicing → LIMIT/OFFSET), `annotations`, etc.

**2. Trigger.** Nothing runs until the QuerySet is *evaluated* — iteration, `len()`, `list()`, `bool()`, repr, etc. These route through `QuerySet._fetch_all()`, which fills `self._result_cache` from `self._iterable_class` (e.g. `ModelIterable`). Subsequent uses hit the cache.

**3. Compile — `Query` → SQL.** The iterable calls `Query.get_compiler(using)`, which returns the backend's `SQLCompiler` (`connection.ops.compiler(...)`; the class name is `Query.compiler`). `compiler.as_sql()`:
- `pre_sql_setup()` → `setup_query()` assigns aliases (`get_initial_alias`), resolves the SELECT columns (`get_select`), then computes `get_order_by()`, splits WHERE/HAVING (`where.split_having_qualify`), and builds GROUP BY (`get_group_by`).
- Each piece is turned into `(sql, params)` by `compiler.compile(node)`, which calls the node's `as_sql(compiler, connection)` — the compilation is delegated polymorphically to every expression/lookup/`WhereNode`. Backends override `as_sql` for dialect differences.
- The clauses are assembled into the final `SELECT ... FROM ... WHERE ... GROUP BY ... ORDER BY ... LIMIT` string with a flat parameter list. Params stay separated from SQL (passed to the driver) to prevent injection.

**4. Execute.** `compiler.execute_sql(result_type)` gets a cursor (`connection.cursor()`), calls `cursor.execute(sql, params)`, and returns/streams rows (`cursor.fetchmany` in chunks via `GET_ITERATOR_CHUNK_SIZE`).

**5. Map rows → objects.** The compiler exposes `select`, `klass_info`, and `annotation_col_map`; `ModelIterable` uses these plus `compiler.results_iter()` to instantiate model instances (handling `select_related` joins, deferred/`only`/`values` fields, and annotations), which `_fetch_all` caches.

Different operations swap the `Query` subclass and compiler: reads use `Query`/`SQLCompiler`, while `.update()`/`.delete()`/bulk insert use `UpdateQuery`/`DeleteQuery`/`InsertQuery` with `SQLUpdateCompiler`/`SQLDeleteCompiler`/`SQLInsertCompiler`.
