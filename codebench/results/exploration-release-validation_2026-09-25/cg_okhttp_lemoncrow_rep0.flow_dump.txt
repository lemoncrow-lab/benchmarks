[assistant] OkHttp models the request/response pipeline as an ordered list of `Interceptor`s driven by `RealInterceptorChain`.

**1. Building the stack** — `RealCall.getResponseWithInterceptorChain()` (RealCall.kt:208) assembles the list in order:
```
client.interceptors        // your application interceptors
RetryAndFollowUpInterceptor // retries + redirects/auth follow-ups
BridgeInterceptor           // app↔network headers (gzip, cookies, Host…)
CacheInterceptor            // serve/store from Cache
ConnectInterceptor          // open/reuse a connection → creates the Exchange
client.networkInterceptors  // (skipped for WebSockets)
CallServerInterceptor       // actually writes request / reads response
```
It then creates a `RealInterceptorChain` at `index = 0` with `exchange = null` and calls `chain.proceed(originalRequest)`.

**2. Recursive descent** — `proceed()` (RealInterceptorChain.kt) is the engine. Each call:
- copies the chain with `index + 1` (and the possibly-mutated request) → `next`,
- invokes `interceptors[index].intercept(next)`.

An interceptor does pre-work, calls `next.proceed(request)` to hand control to the interceptor below it, then does post-work on the returned `Response`. So the request travels **down** the list and the response bubbles back **up** — nesting, not a flat loop. An interceptor may short-circuit (e.g. `CacheInterceptor` returning without proceeding) or call `proceed` repeatedly (`RetryAndFollowUpInterceptor`).

**3. Invariants enforced by `proceed`:**
- `check(index < interceptors.size)` — the chain must terminate at `CallServerInterceptor` (which never proceeds).
- Once an `Exchange` exists (network interceptors and below), it asserts each network interceptor calls `proceed()` **exactly once** and keeps the same host/port.

**Application vs network interceptors:** application interceptors run with `exchange == null` (once per call, see full response regardless of retries/redirects); network interceptors run after `ConnectInterceptor` established the `Exchange`, so they see the real on-the-wire request and each redirect/retry.

Net effect: `CallServerInterceptor` produces the raw response, and it flows back up through connect → cache → bridge → retry → your interceptors, each unwinding its post-processing.
